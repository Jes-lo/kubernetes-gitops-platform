# Reproducibility Guide

This document describes how to reproduce the Kubernetes GitOps Platform from a clean local environment while preserving the project's security boundaries.

The bootstrap process is designed around these principles:

- infrastructure and platform configuration are version controlled;
- credentials are generated independently for every environment;
- private credentials never enter Git;
- GitHub deploy keys are read-only;
- existing Kubernetes clusters and Argo CD credentials are not overwritten;
- Argo CD remains the reconciler for application and platform workloads;
- runtime Kafka credentials are generated by Strimzi rather than stored in source control;
- destructive cleanup is never part of the default bootstrap workflow.

---

## 1. Reproducibility Scope

The repository can reproduce the following local platform:

~~~text
Docker
  |
  v
kind Kubernetes cluster
  |
  v
Terraform
  |
  v
Argo CD
  |
  +--> Demo application
  |
  +--> Strimzi Operator
          |
          v
        Kafka
          |
          +--> KafkaNodePool
          +--> KafkaTopic
          +--> KafkaUser
          +--> runtime-generated TLS credentials
~~~

The current local development topology uses:

- kind cluster: `kubernetes-gitops-dev`
- Kubernetes: `v1.36.4`
- Terraform: `1.16.x`
- Argo CD Helm chart: `10.9.2`
- Strimzi Operator: `1.2.0`
- Kafka: `4.3.1`
- Kafka metadata version: `4.3-IV0`

Pinned versions and dependency locks are kept in version-controlled configuration wherever applicable.

## 2. What Is Reproduced

A clean bootstrap creates or reconciles:

1. the pinned kind Kubernetes cluster;
2. the Argo CD namespace and Helm release through Terraform;
3. Argo CD repository authentication from an externally generated deploy key;
4. Argo CD AppProjects;
5. the demo application;
6. the Strimzi Operator;
7. required Strimzi CRDs;
8. the Kafka platform;
9. Kafka persistent storage;
10. the `platform-events` topic;
11. the `demo-client` KafkaUser;
12. runtime TLS credentials generated by Strimzi.

The repository does **not** contain private keys, Kafka passwords, generated TLS private keys, Terraform state, or kubeconfig files.

## 3. Security Model

### Unique credentials per environment

Every environment receives a newly generated SSH deploy key.

Example environment names:

~~~text
dev
dev-rebuild
test
portfolio-demo
~~~

Environment names must be DNS-safe:

- lowercase letters;
- numbers;
- hyphens;
- start and end with an alphanumeric character;
- maximum 40 characters.

Private keys are generated under:

~~~text
~/.config/kubernetes-gitops-platform/keys/<environment>/argocd-repo
~~~

They are intentionally stored outside the Git repository.

### GitHub access

Only the public key is registered with GitHub.

Deploy keys are required to be:

~~~text
read_only = true
verified  = true
~~~

The scripts verify the deploy key cryptographic identity before using or revoking it.

### Argo CD authentication

Repository authentication is created as a Kubernetes Secret at runtime.

The private SSH key:

- is not written to a repository file;
- is not printed;
- is not committed;
- is streamed directly into Kubernetes;
- is never allowed to replace another repository credential automatically.

### Kafka credentials

Kafka client credentials are generated by Strimzi at runtime.

The repository contains the declarative `KafkaUser`, but not the resulting:

~~~text
user.key
user.crt
user.p12
user.password
~~~

The Kafka cluster CA credentials are also generated at runtime.

## 5. Clean Bootstrap Workflow

Choose a new environment name.

Example:

~~~bash
export ENVIRONMENT=dev-rebuild
~~~

### Step 1 - Generate a new deploy key

~~~bash
make key ENV="$ENVIRONMENT"
~~~

This creates a new credential outside the repository.

Existing credentials are never overwritten.

### Step 2 - Register the public key

~~~bash
make register-key ENV="$ENVIRONMENT"
~~~

The script registers only the public key and verifies that GitHub created it as read-only.

### Step 3 - Create the Kubernetes cluster

~~~bash
make cluster
~~~

If the cluster already exists, the script does not delete or recreate it.

It verifies:

- expected node count;
- kubeconfig context;
- Kubernetes API availability;
- all nodes are `Ready`.

### Step 4 - Bootstrap Argo CD

~~~bash
make argocd
~~~

Terraform performs initialization, validation, planning, and application using the committed dependency lock file.

The Kubernetes provider uses the explicit expected context.

If an `argocd` namespace already exists but the corresponding Terraform state is absent, the bootstrap stops instead of silently adopting an unmanaged installation.

Terraform plan files are created temporarily outside the repository.

### Step 5 - Configure repository authentication

~~~bash
make repo-auth ENV="$ENVIRONMENT"
~~~

This step requires the environment-specific private key created in Step 1.

The script verifies:

- the private key exists;
- the private key is outside the repository;
- private-key permissions are restricted;
- private and public keys match;
- the Kubernetes context is correct;
- `github.com` is present in Argo CD trusted SSH hosts;
- the expected deploy key exists in GitHub;
- its cryptographic identity matches the local public key;
- the GitHub deploy key is verified;
- the GitHub deploy key is read-only.

The script refuses to replace an existing Argo CD credential for the same repository.

### Step 6 - Bootstrap GitOps resources

~~~bash
make gitops
~~~

The bootstrap order is intentionally controlled:

~~~text
AppProjects
   |
   v
Base Applications
   |
   v
Strimzi Operator
   |
   v
Strimzi CRDs
   |
   v
Kafka Application
   |
   v
Kafka Ready
~~~

Kafka resources are not enabled until the required Strimzi CRDs are established.

Application and platform workloads remain reconciled by Argo CD.

The bootstrap does not directly apply Kafka workload manifests.

### Step 7 - Validate the platform

~~~bash
make validate
~~~

Validation includes:

- Kubernetes API availability;
- Kubernetes node readiness;
- Argo CD Application synchronization and health;
- repository credential cardinality;
- Strimzi Operator availability;
- required Strimzi CRDs;
- Kafka Ready condition;
- Kafka runtime version;
- Kafka metadata version;
- KafkaNodePool configuration;
- Kafka broker Pods;
- Kafka persistent volumes;
- KafkaTopic state;
- KafkaUser state;
- expected runtime Secret keys;
- absence of tracked Kubernetes Secret manifests;
- absence of tracked Terraform state.

A successful run ends with:

~~~text
failures=0
PASS: platform validation completed successfully
~~~

### Step 8 - Run functional Kafka validation

~~~bash
make validate-kafka
~~~

This creates a temporary Kafka client Pod and validates:

- TLS encryption;
- client certificate authentication;
- authorized producer access;
- authorized consumer access;
- exact message delivery;
- least-privilege ACL enforcement.

The positive path produces a unique test message and confirms that the same message can be consumed.

The negative path attempts an unauthorized `DescribeConfigs` operation and expects Kafka authorization to reject it.

The temporary validation Pod is removed after the test.

## 6. Convenience Bootstrap

After a unique deploy key has already been generated and registered, the remaining bootstrap sequence can be executed with:

~~~bash
make bootstrap ENV=<environment>
~~~

The workflow remains explicitly sequential:

~~~text
preflight
   |
   v
cluster
   |
   v
argocd
   |
   v
repo-auth
   |
   v
gitops
   |
   v
validate
~~~

Credential generation and GitHub registration are intentionally excluded from `make bootstrap`.

This prevents a convenience command from silently generating, replacing, or rotating security credentials.

The Kafka functional validation also remains explicit:

~~~bash
make validate-kafka
~~~

Even if GNU Make is invoked with parallel execution, for example:

~~~bash
make -j8 bootstrap ENV=<environment>
~~~

the main bootstrap target invokes each stage sequentially.

## 7. Idempotency

The bootstrap scripts are designed to be safely repeatable.

### Existing kind cluster

`create-cluster.sh`:

- detects an existing cluster;
- does not delete it;
- does not recreate it;
- verifies the expected node count;
- verifies Kubernetes node readiness.

### Existing Argo CD

`bootstrap-argocd.sh`:

- initializes Terraform with the committed dependency lock file;
- validates Terraform configuration;
- verifies Terraform state ownership;
- runs a Terraform plan;
- performs no infrastructure change when configuration already matches reality.

An existing Argo CD installation without matching Terraform state is not automatically adopted.

### Existing GitOps resources

`bootstrap-gitops.sh` applies the version-controlled Argo CD control-plane resources declaratively.

Existing resources normally report:

~~~text
unchanged
~~~

Argo CD remains responsible for reconciling application and platform workloads.

### Existing repository credentials

`configure-repo-auth.sh` intentionally behaves differently from other idempotent components.

It refuses to replace an existing Argo CD repository credential for the same repository.

Credential rotation must therefore be a deliberate operation rather than an automatic side effect of bootstrap.

## 8. Credential Revocation

GitHub deploy keys can be revoked with:

~~~bash
CONFIRM_REVOKE=argocd-repo-<environment> \
  ./scripts/revoke-repo-deploy-key.sh <environment>
~~~

The revocation script verifies:

- repository identity;
- environment name;
- deploy key title;
- local public-key identity;
- GitHub public-key identity;
- GitHub key ID;
- explicit operator confirmation.

If an environment-specific Argo CD repository Secret exists, the script refuses the obvious active-use case instead of revoking the credential automatically.

The GitHub deploy key and the local credential have separate lifecycles.

Revoking the GitHub deploy key does not automatically delete the local key files.

After confirming that the credential is no longer needed, local files can be removed explicitly:

~~~bash
rm -f \
  ~/.config/kubernetes-gitops-platform/keys/<environment>/argocd-repo \
  ~/.config/kubernetes-gitops-platform/keys/<environment>/argocd-repo.pub

rmdir \
  ~/.config/kubernetes-gitops-platform/keys/<environment> \
  2>/dev/null || true
~~~

A rebuilt environment should receive a new credential instead of copying an old private key from another environment.

## 9. Terraform State

The local laboratory currently uses local Terraform state:

~~~text
terraform/bootstrap/terraform.tfstate
~~~

This file is intentionally ignored by Git.

It must never be committed.

The current design is appropriate for this local development laboratory, but it is not a production-grade state-management strategy.

A production environment should use an encrypted remote backend with controls such as:

- authentication and authorization;
- state locking;
- encryption at rest;
- versioning;
- backup and recovery;
- restricted administrative access.

The bootstrap script also refuses to adopt an existing Argo CD installation when the corresponding Terraform state is absent.

This protects against accidental ownership of infrastructure that Terraform did not create or already manage.

## 10. Kafka Storage and Availability

The Kafka platform declares three logical Kafka replicas through the `KafkaNodePool`.

The local kind topology contains:

~~~text
1 control-plane node
2 schedulable worker nodes
~~~

The control-plane node remains dedicated to Kubernetes control-plane responsibilities.

Kafka Pods are therefore scheduled across only two worker nodes.

This means:

~~~text
3 Kafka replicas != 3 independent infrastructure failure domains
~~~

The environment demonstrates:

- Kafka replication;
- KRaft operation;
- Kubernetes scheduling;
- Strimzi reconciliation;
- persistent volumes;
- TLS authentication;
- authorization controls.

It must **not** be represented as production-grade high availability.

A production architecture would require appropriately separated infrastructure failure domains.

### Kafka persistent storage

Kafka uses persistent claims managed through the local kind StorageClass.

The current laboratory configuration uses:

~~~text
StorageClass: standard
Kafka PVCs:   3
Size:         1 Gi each
deleteClaim:  false
~~~

The persistent claims remain after Kafka resources are removed unless they are explicitly deleted.

Because the kind StorageClass is backed by local development storage, it should not be treated as production-grade persistent storage.

## 11. Container Image Availability

During initial Kafka deployment, the Strimzi Kafka image experienced transient download timeouts from the external registry backing infrastructure.

The affected image was:

~~~text
quay.io/strimzi/kafka:1.2.0-kafka-4.3.1
~~~

The issue was external image availability rather than a Kafka or GitOps configuration failure.

The architecture does not depend on manually loading container images into kind.

If registry availability prevents Kafka from becoming Ready:

1. inspect Kafka Pods;
2. inspect namespace events;
3. identify image pull errors;
4. retry when registry connectivity is restored;
5. optionally preload the exact expected image into kind as a troubleshooting contingency.

The GitOps bootstrap intentionally surfaces Pod and event diagnostics instead of silently modifying the architecture.

Manual image preloading should remain a contingency, not part of the normal desired-state workflow.

## 12. Destructive Operations

There is intentionally no default Make target such as:

~~~text
make destroy
~~~

Cluster deletion is destructive and remains an explicit operator decision.

If local destruction is genuinely intended, the kind cluster can be removed manually:

~~~bash
kind delete cluster --name kubernetes-gitops-dev
~~~

Deleting the kind cluster removes the local Kubernetes runtime environment.

It does not automatically revoke GitHub deploy keys or delete local credential files.

The following lifecycles are intentionally separate:

~~~text
Kubernetes cluster lifecycle
GitHub deploy-key lifecycle
local private-key lifecycle
Terraform state lifecycle
~~~

Each destructive action must therefore be deliberate.

## 13. Security Boundaries

The following material must never be committed to the repository:

~~~text
SSH private keys
Kafka private keys
Kafka passwords
generated TLS credentials
Terraform state
kubeconfig files
.env secrets
temporary Terraform plans
~~~

Before committing reproducibility changes, run:

~~~bash
make check
~~~

The preflight and validation scripts verify important repository safety conditions, including:

- Terraform state is not tracked;
- kubeconfig files are not tracked;
- OpenSSH private-key material is not tracked;
- pinned kind node images are present;
- the Terraform dependency lock file exists;
- the Terraform dependency lock file is tracked;
- Kubernetes Secret manifests are not tracked;
- runtime credential values are not printed by validation scripts.

Credential files must remain outside the source tree.

Environment-specific credentials must not be copied from one environment into another.

## 15. Functional Validation Result

The functional Kafka validation must demonstrate both an allowed operation and a denied operation.

Expected positive result:

~~~text
mTLS connection            PASS
producer write             PASS
consumer read              PASS
exact message delivery     PASS
~~~

Expected negative authorization result:

~~~text
DescribeConfigs            BLOCKED
~~~

The negative test demonstrates that successful authentication does not imply unrestricted authorization.

The `demo-client` user can perform the operations explicitly allowed by its ACLs while unauthorized administrative/configuration access remains blocked.

The ephemeral validation Pod must also be removed after the test.

## 16. Reproducibility Model

The platform intentionally separates three categories of state:

~~~text
Version-controlled desired state
        +
environment-specific generated credentials
        +
runtime-generated security material
~~~

### Version-controlled desired state

Examples include:

- kind cluster configuration;
- Terraform configuration;
- Terraform dependency lock file;
- Argo CD AppProjects;
- Argo CD Applications;
- Strimzi configuration;
- Kafka resources;
- application manifests;
- validation and bootstrap scripts.

### Environment-specific generated credentials

Examples include:

- GitHub SSH deploy private key;
- corresponding GitHub public deploy key;
- Argo CD repository Secret created from that private key.

These credentials are unique to the environment and remain outside Git.

### Runtime-generated security material

Examples include:

- Kafka client private keys;
- Kafka client certificates;
- PKCS12 client stores;
- Kafka user passwords;
- Kafka cluster CA certificates;
- Kafka cluster CA private material.

These are generated by Strimzi inside Kubernetes.

They are not copied from previous environments and are not committed to source control.

---

## 17. Clean Environment Principle

A newly rebuilt environment should receive:

~~~text
new GitHub deploy key
new Argo CD repository Secret
new Strimzi-generated Kafka credentials
new Strimzi-generated CA material
~~~

It should **not** require:

~~~text
an old SSH private key
an exported Kubernetes Secret
an old Kafka password
an old Kafka certificate
an old Terraform state file from another environment
~~~

This allows the architecture and desired state to remain reproducible without making credentials reproducible.

Credentials are intentionally unique.

Configuration is reproducible.

Secrets are regenerated.
